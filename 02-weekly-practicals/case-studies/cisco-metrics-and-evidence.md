# Cisco metrics and evidence case study

## Case purpose

The Week 4 Cisco case study is used as a quality check for cyber-risk reporting: a polished metric or chart can still mislead when its data definitions, coverage, categories, or baseline are unclear.

## Applied lessons

| Lesson | Application to the DJI coursework analysis |
| --- | --- |
| Verify that data supports the conclusion. | Public identity-attack or GNSS-interference material indicates context; it does not establish DJI incident frequency. |
| State what is included and excluded. | Risk counts, cost figures, and incident categories need explicit scope and definitions. |
| Do not mix unlike observations. | Confirmed incidents, alerts, estimates, and potential findings should not be shown as one trend. |
| Establish a stable baseline. | A KPI needs a defined population, measurement method, owner, and starting value before targets are interpreted. |
| Make uncertainty visible. | ARO, SLE, treatment cost, and control effectiveness should be labelled as evidence-backed values or scenario assumptions. |
| Use visualisations to answer a decision question. | A figure should show what decision it informs, its calculation basis, and the action it suggests. |

## Practical consequence

The course work uses ranges, confidence ratings, source types, captions, and limitations to avoid false precision. A quantitative result is useful only when the reader can trace the reasoning, see the uncertainty, and understand what additional evidence would change the decision.
